# Analytic file amendments

**Frozen:** 2026-08-31 at Task 2.8. `data/analytic-v1.rds`, hash pinned in
`provenance/analytic-v1.sha256`. `make.R` re-hashes the rebuilt file on every
run and fails if it drifts.

---

## The rule

After the freeze, **any change to the contents of the analytic file requires a
dated, numbered amendment appended to this file**, stating:

1. **What changed** -- which column(s), which hospitals, the old and new values
   or the nature of the change.
2. **Why** -- the defect or new information that forced it.
3. **What had been seen at the time** -- specifically, whether any modelling
   result that the change could affect had already been computed. Changing the
   analytic file after seeing a result it influences is not permitted; the
   amendment must state that no such result had been seen, or the change is
   invalid.
4. **The new version and hash** -- the file becomes `analytic-v2.rds` (then
   `-v3`, ...), `provenance/analytic-v1.sha256` gains the new line, and every
   downstream task re-runs against the new version.

A change that only *adds* a column derived entirely from already-frozen columns
(a transformation, an interaction) does **not** need an amendment -- it is a
modelling choice, made in Phase 3, on top of the frozen file. An amendment is
for changing what the frozen file *records*: a corrected value, a re-drawn
imputation, an added or removed covariate, a changed frame.

The admission gates (`provenance/admission-gates.md`) have their own, stricter
amendment rule for thresholds; that rule is unchanged and takes precedence for
anything it covers.

### Rule 2 — defect repairs after results (2026-10-01, Task S0.2)

Rule item 3 above forbids changing the file after seeing a result it influences.
The critical review of 2026-10-01 found a defect in how the file was built (the
Connecticut ZIP-to-tract allocation, `R/catchment.R`), discovered after every
result had been seen. Item 3 would make that error impossible to correct. It is
therefore relaxed for **defect repairs only**: a repair is permitted after
results when its amendment records (a) the defect and the evidence for it,
(b) the old and new values, (c) the new version and hash; the old results are
kept in `archive/` (Task S0.1); and every downstream stage reruns. A repair may
not be chosen for its effect on a result, so the rule that decides whether a
repair produces a new version is fixed in advance
(`second-pass-preregistration.md` sec 7). Modeling choices remain under item 3
unchanged.

## Amendments

### Amendment 1 — `analytic-v2.rds` (2026-10-01, Task S0.4, under rule 2)

1. **What changed.** Catchment-weighted Block B covariates (every
   `*_catch_tract`, `*_catch_county` and `*_catch_tract_wt` column, plus
   rurality and primary-care density at catchment grain) for **197 of 2,801
   hospitals**: all **25 in Connecticut** (largest move 0.71 SD, SVI theme 4 at
   tract grain) and **13 elsewhere** (largest 0.067 SD). The contract-labor
   imputations (`cl_share_mi_01`–`_20`) changed for **157 of the 158 imputed
   hospitals**, because the imputation model's Block B predictors changed and
   the same seed then draws a different chain; no observed value changed.
   Column-by-column counts and largest moves: `output/tables/ct-allocation-check.csv`
   (regenerated by stage 14's comparison, recorded in the task note).
2. **Why.** Two defects in `build_zcta_tract_alloc()` (`R/catchment.R`), found by
   the critical review of 2026-10-01. (a) SVI 2022 keys Connecticut tracts by
   the 2022 planning regions and the 2020 relationship file by the legacy
   counties; the two share no tract IDs, so every Connecticut slice missed its
   population and fell back to land area. (b) A ZCTA in which some slices had a
   population and others did not normalised people and square metres together.
   The review's spot check found no realized case of (b); the full comparison
   finds 13 hospitals affected by it.
3. **What had been seen.** Every result of Phases 3–5 and the September 30
   draft. Item 3 of the rule would forbid this; rule 2 permits it as a defect
   repair. The rule that decided adoption (any frame hospital's value moving by
   more than 1e-8) was fixed in `second-pass-preregistration.md` sec 7 before
   the comparison was computed. The v1 file and everything built on it are in
   `archive/draft-2026-09-30/`.
4. **New version and hash.** `data/analytic-v2.rds`, pinned in
   `provenance/analytic-v1.sha256` beside the v1 lines. Every downstream stage
   reruns against it; the cache keys (Task S0.3) force that, since the file's
   path and content are part of every key.
