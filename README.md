# Community disadvantage and hospital patient safety scores

A national study of 2,569 U.S. hospitals that asks how much of the variation in CMS's PSI-90 patient-safety composite is explained by the communities hospitals serve, and whether that answer survives the choice of model. Built by Carl Jacobsen as a research intern at the Jewish Healthcare Foundation (Pittsburgh), May to October 2026, and released with the Foundation's permission.

## What it found

- **Community measures explain 3.3% of PSI-90 variation (2.5% to 4.8%), and their direction is unsettled.** No stable sign emerges across the 736 registered specifications or the 194 near-optimal models in the main Rashomon set (the models that fit the data almost as well as the best one), so the report advises against hospital-level community adjustment on public data.
- **Penalties fall harder on disadvantaged catchments.** Under the FY2026 Hospital-Acquired Condition Reduction Program, hospitals serving the most deprived fifth of catchments were penalized at 1.39 times the rate of those serving the least deprived (1.14 to 1.71).

The full write-ups are in `docs/`: the report ([Variance in Patient Safety.pdf](docs/Variance%20in%20Patient%20Safety.pdf)) and the technical supplement ([Technical Supplement.pdf](docs/Technical%20Supplement.pdf)), which covers methods, sensitivity tables and the number registry.

## How it is built

The hospital file links PSI-90 to hospital structure (Block A), the social and geographic context of each hospital's catchment (Block B), and the policy and legal environment (Block C), drawing on 35 admitted public data files (38 were tried; the three exclusions and their reasons are recorded in `provenance/sources.csv`). Whether a finding depends on modeling choices is tested two ways: a specification curve over 736 registered specifications, and model class reliance bounds (the smallest and largest importance any near-optimal model places on a block) across the Rashomon set, with the set's tolerance chosen by bootstrap.

Every number in both documents is regenerated by `make.R` from the raw downloads and checked against a registry before the documents are built, and the analytic file is hashed and pinned. The specification registry was committed before the specification curve was fitted, and the preregistrations for the Rashomon, cluster and archetype analyses are in `provenance/`.

## Authorship

Study design, data admission, modeling decisions and validation are mine; the code was written with an AI coding assistant (Claude Code). Two external reviewers read the analysis before circulation.

This public repository is a single-commit snapshot of the project's working history (96 commits). Internal engagement notes were removed and the names of Foundation staff in the provenance notes were replaced with their roles.

## Data and terms

No data are committed. `provenance/sources.csv` records the URL, access date, license and SHA-256 hash of every input, and `python3 provenance/redownload-test.py` re-fetches them. County Health Rankings & Roadmaps data are used under its non-commercial terms with the required citation: University of Wisconsin Population Health Institute. County Health Rankings & Roadmaps. www.countyhealthrankings.org. A U.S. Census API key is read from the `CENSUS_API_KEY` environment variable and is never recorded.

# Build notes

## Run it

```
Rscript make.R            # every stage whose inputs are present
Rscript make.R --list     # stages and whether their inputs are on disk
Rscript make.R --stage 1  # one stage
Rscript make.R --release  # every stage, no skips, then build the report and supplement
```

Run from this directory. `make.R` refuses to run from anywhere else rather
than writing outputs into the wrong tree.

**A fresh clone is a clean run, not a failure.** `data-raw/` is not in the
history — the archived downloads are 144 MB and growing, and the whole point
of the provenance table is that they are re-downloadable. A stage whose inputs
are absent is skipped with its missing files named. To get them back, work
from `provenance/sources.csv`.

## Layout

```
make.R                  single driver: raw inputs -> every number and figure
DESCRIPTION             the declared dependency set (renv snapshots explicitly)
renv.lock               resolved dependency versions, R 4.5.0
R/                      functions and stages, one file per stage
data-raw/               archived downloads, never edited, never committed
data/                   built tables; the analytic file is hashed and pinned (analytic-v2 since S0.4)
provenance/             source table, admission gates, spike notes, exclusion log
output/figures/
output/tables/          every stage tees its numbers here
report/                 report sections, claims table; report/supplement/ the technical supplement
tools/                  report builder, claim-guard frozen prose (sep30/, oct7/), helpers
```

## The rules this repo enforces

1. **Every number regenerates from `make.R`.** Nothing is transcribed by hand.
   If a number appears in prose, `make.R` produced it. Each stage tees its
   console output to `output/tables/`, so the numbers are a file on disk and
   not a terminal that has scrolled away.
2. **`renv` from the first commit, relative paths only.** Retrofitting
   reproducibility is what went wrong on CASH2; it was cheap to avoid here.
3. **Associational language only.** "Associated with," never "causes."
4. **Nothing gets dropped quietly.** Unmatched hospitals are enumerated;
   a source that was tried and rejected stays in `sources.csv` with its
   `exclusion_reason` filled in.
5. **No importance claim rests on marginal permutation alone.**
6. **The published PSI-90 is a smoothed estimate, and it is the outcome.**
   The per-hospital reliability λᵢ is the project's scalar approximation to
   CMS's smoothing, not a quantity CMS reports, and its accuracy for this
   release is unknown. Every analysis that uses it (weighted and
   errors-in-variables fits, the choice of the main Rashomon set, the payment
   simulation's score draws) is reported beside one that does not.
7. **Recover before imputing.** A value obtainable from raw HCRIS or an
   adjacent fiscal year is observed data, flagged by source.
8. **The analytic file is pinned.** It was frozen at Task 2.8 as
   `analytic-v1` and is now `data/analytic-v2.rds` (amendment 1, the
   Connecticut allocation, Task S0.4). It is a build product; its hash is
   pinned in `provenance/analytic-v1.sha256` (one line per version) and
   `make.R` fails if a rebuild drifts. Changing what the file records requires
   a numbered amendment in `provenance/amendments.md` and a version bump.
9. **The report's numbers and meanings are checked before it is built.**
   Stage 39 registers every number the report and supplement cite and fails
   on any unregistered token, and its claim guards fail on meanings the
   October 1 review and the October 7 audit retired. `report/claims.md` is
   the claim-to-evidence table the prose is read against.

## Provenance

`provenance/sources.csv` is the table Phase 1 is graded on: a stranger holding
only that file can re-download every input. Schema and helpers are in
`R/provenance.R`; `make.R` re-hashes every archived file on each run and
reports any drift. That claim is executable — `python3 provenance/redownload-test.py`
re-fetches every source from the table alone and diffs the hashes (Task 1.7).

Phase 0's notes — `spike-outcome.md`, `spike-structure.md`, `spike-context.md`,
`admission-gates.md`, `plan-amendments.md`, `phase0-closeout.md`,
`phase1-readiness.md` — are in `provenance/`. Their numbers come from stage 1.
